**About:** This project is designed to keep the WIFI connection alive while the adapter is in monitor mode state all from userspace.

**The need:** This can solve the need for two adapters for WIFI penetration testing and make learning monitor mode easier without the need to install kernel drivers.

**How it works:** This project consists of two main binaries .elf and .so

**.elf:**  
The first binary acts as the loader and injector of the second binary and is the heart of the project.
It serves the system as a network stack it handles requests, sockets, connections, retries and more.
The first thing the elf does is ask what WIFI it should connect to and what is the password for that WIFI.
It then preforms the usual process of connecting to the WIFI as described at the end.
After a successful connection to the WIFI network the elf waits for programs to be opened. Once they are opened the elf kills them and restart them and inject the .so using the LD_PRELOAD variable. 
And finally i waits for requests and traffic.

**.so:**  
The second binary is the actual bridge between the network stack and the target binary.
It routes the requests by overriding the default entries for functions like socket() and more to functions that route the request to the elf that process that request.
The functions can be made asyc and sync.


**Usual WIFI connection process:**  
Step 1: Probe - The client asks the host AP for its information (what is supported, what protocol and stuff like that).

Step 2: Auth - The client sends an Authentication packet to the ap saying he is interested in connecting to this AP.

Step 3: Assoc - At this stage the client must add the security that will be used for this connection, what rates he supports and more optional data.

Step 4: Handshake - This step depends on the security type that was chosen(SAE or non SAE or less common ways) for this step i will cover the non SAE. non SAE handshake consists of 4 main packets(M1,M2,M3,M4).  
The first packet(M1) is sent by the host to the client and it contains A nonce(randomly generated by host), counter, info flags.  
From M1 the client constructs the M2 packet that contain S nonce(randomly generated by client), MIC, counter, and optional RSN info. The MIC sent in M2 is calculated based on the cipher that was chosen in step 3 but overall it is calculated from both nonce, password, mac and the network name.  
The M3 packet is then sent by the host to the client with the following data: MIC, counter, encrypted GTK, and optional RSN info the client decrypt the GTK using the KEK and installs the key.  
The last packet that is sent for this handshake is the M4 packet. The M4 is sent by the client to the host to signal success to the host and mark the start of the connection.
